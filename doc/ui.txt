1. INTRODUCTION                                          *ui-introduction*

ui.nvim is the frame around the window: statusline, tabline and theme
assembly.

The dividing line this plugin draws is worth stating plainly:

    Content lives inside the window. ui.nvim paints the frame around it.

Cursorline, mode tinting, indent guides and occurrence highlighting are
content; they work with any statusline and are out of scope here. Statusline,
tabline and theme assembly are frame.

==============================================================================
2. REQUIREMENTS                                          *ui-requirements*

    Neovim      0.10+
    lib.nvim    required
    NvChad      not required by this plugin's own code (v2.5, if present)

As of roadmap step 5, this plugin's own code no longer needs NvChad to load,
assemble, render, OR move buffers and tabs: `ui.statusline.render` is the
`vim.o.statusline` / `generate()` walk that used to be entirely
`nvchad.init` + `nvchad.stl.utils.generate()` (step 4; step 3 had already
ported the primitives and separator reads that walk itself uses), and
`ui.bindings.keymaps.tabufline.state` is the `vim.t.bufs` bookkeeping and
`close_buffer()`/`move_buf()` that used to be entirely
`nvchad/tabufline/lazyload.lua` + `nvchad.tabufline` (step 5). Verified
headless, NvChad absent from the runtimepath: all six statusline variants
assemble and render end to end, and buffer/tab navigation works against real
buffers and tabs.

What is NOT true yet: that a real install of this plugin renders without
NvChad. Nothing outside this plugin's own tests calls
`ui.statusline.render.enable()` -- the reference host this plugin was
extracted from still wires `chadrc.lua` to NvChad's own renderer, and
rewiring that host is roadmap step 7, not done. `base46`/`base46.themes`
remain a genuine soft dependency for the theme (step 6).

Soft, each blanking only its own statusline segment: `nvim-web-devicons`,
`neotest`, `casedesk.nvim`.

3. SETUP                                                        *ui-setup*

Two entry points, at different times.

`ui.config.setup()` runs while NvChad boots, through `chadrc`, and answers
"which theme, which layout": >lua
    -- lua/chadrc.lua
    local ok, config = pcall(function()
      return require("ui.config").setup()
    end)

    return {
      base46 = config.base46,
      ui = { statusline = config.ui.statusline },
    }
<
`ui.setup(opts)` runs afterwards, from your own config, and answers "which
keymaps and commands exist": >lua
    require("ui").setup({ all = true })
<
Nothing is on by default -- the two halves are independently useful, so the
flags are explicit: >lua
    require("ui").setup({ usrcmds = true })  -- commands only, no keymaps
<
    all       (boolean) shorthand for every flag below
    keymaps   (boolean) buffer/tab navigation and tabline mappings
    usrcmds   (boolean) the :UI command and theme management

Theme overrides go to `ui.config.setup`, not here: >lua
    require("ui.config").setup({
      base46 = { theme = "rosepine", transparency = true },
    })
<

4. COMMANDS                                                  *ui-commands*

                                                                       *:UI*
:UI theme {name}
    Switch to a theme and reload every highlight. {name} completes over the
    installed base46 themes, read at the moment <Tab> is pressed.

:UI themes
    List available themes, marking the active one.

:UI toggle
    Swap between the two themes in `base46.theme_toggle`.

:UI transparency
    Toggle background transparency.

:UI status
    Current theme, transparency state and statusline variant.

:UI help
    The subcommand list, in a float.

No subcommand takes a range or a count: each acts on global state, where
neither has a meaning.

5. KEYMAPS                                                    *ui-keymaps*

Registered by `ui.setup({ keymaps = true })`.

    <Tab>          next buffer
    <S-Tab>        previous buffer
    <leader>bc     close the current buffer, keeping the window layout

    <leader>tr     move the current buffer right in the tabline
    <leader>tl     move it left
    <leader>tt     move the current buffer into a new tab

Every one is wrapped: a failure notifies and returns rather than raising,
because these sit on keys pressed constantly and a traceback out of <Tab>
makes the editor feel broken.

`<leader>tr` and `<leader>tl` go through `ui.bindings.keymaps.tabufline.state`
(own code, step 5, not `nvchad.tabufline`) -- they work with NvChad entirely
absent.

6. STATUSLINE VARIANTS                                       *ui-variants*

Six layouts ship. Which one is assembled is the STATUSLINE_VARIANT constant in
`lua/ui/config/init.lua`, readable through `ui.config.get_variant()`. It is a
setup-time choice: NvChad reads the assembled table once while booting.

    normal           NvChad's own statusline, unmodified (the default)
    base             minimal: cursor, working directory, progress
    lspbased         LSP-aware breadcrumbs plus the enhanced segments
    custom           the older custom breadcrumb implementation
    custom_light     "custom", assembled through a merge-based setup()
    custom_minimal   "custom", built on NvChad's gen_block pattern

An unknown name falls back to `normal` with a notification rather than
throwing. |:checkhealth| reports the active variant and whether its module
resolves, because that fallback is otherwise quiet.

==============================================================================
7. HEALTH                                                     *ui-health*

>vim
    :checkhealth ui
<
Five sections: dependencies (lib.nvim required; NvChad presence reported as
information, not a dependency check, since step 4; `base46`/`base46.themes`
still genuinely soft; `nvchad.tabufline` gone from this list entirely, step
5), the assembled configuration, this plugin's own statusline render
entrypoint (resolves? renders the "default" theme's fallback modules without
NvChad?), which submodules `setup()` turned on (buffer/tab navigation
included, under `keymaps`), and the soft dependencies each statusline
segment needs.

The dependency section returns early only if lib.nvim itself is missing or
incomplete -- everything below it needs lib.nvim, and a missing NvChad no
longer stops the report (it stopped being fatal at step 4).
